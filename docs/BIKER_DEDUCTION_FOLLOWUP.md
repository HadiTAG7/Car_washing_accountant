# إسناد خصم سويتر إلى البايكر

قرار هادي 29 أكتوبر 2026، مرجع الرسالة `01a18461-252a-7032-b787-34a1206a9171`، يجيز معالجة الوقائع التاريخية من 29 أغسطس إلى 28 أكتوبر. لا يعرّف سياسة عقوبات مستقبلية.

المسار الإداري في «الجودة والمخالفات»: معاينة، مراجعة العامل والدليل، تسجيل، ثم قراءة منفصلة للتحقق. الأفعال المدعومة في واجهة الخادم الحالية: `bikerDeductionPreview`، و`bikerDeductionSave`، و`bikerDeductionRead`. ليست أدوات MCP جديدة ولا استدعاءً مباشرًا لسويتر.

## مصدر الواقعة ووحدتها

- `sourceKind: metrics`: صف فعلي في أحدث لقطة تفاصيل سويتر المحفوظة للبند؛ المجاميع وحدها لا تكفي. المخالفات والأضرار والتعويضات تحتاج مبلغ SAR موجبًا. إلغاء البايكر واقعة بالعدد، ويجوز بقاء المبلغ null.
- `sourceKind: booking`: سبب حجز صريح محفوظ عبر استيراد العمليات الحالي، مطابق للخام والحجز والدفعة. السببان المسموحان: `Biker Refused Wash` و`Biker delay caused cancellation or postponement`. التصنيف **بقرار هادي من سبب الحجز**، والمطابقة مع Compensations تظل معلقة. المبلغ null إلا بدليل فاتورة الحجز الفعلي أدناه. الحالة «ألغاه المسؤول» وحدها لا تكفي، والحادث أو الصيانة أو عدم رد العميل لا يثبت ذنب العامل.
- لا تحويل من عدد الإلغاءات إلى 20 أو 23 ريالًا، ولا إلى عمولة 4.50 ريال. لا تُستخدم مخالفات الملصقات والأدوات كإلغاءات غسيل.
- لا يتغير عقد المرسل أو بصماته أو مفاتيحه. وصول تفاصيل Compensations لاحقًا عبر المسار الموقع القائم يتيح تصحيح الواقعة نفسها مع بقاء الأصل والتاريخ.

## التخزين ومنع التكرار

امتداد لمتابعة واقعة المصدر داخل مخزن الحالات الإداري الموجود `quality_objections`، بنوع مستقل `source_biker_deduction_v1` ومفتاح `biker-deduction-<hash>`. ليس اعتراضًا ولا قيدًا ماليًا. يستبعده قارئا الاعتراضات والتنبيهات من حالات الاعتراض. الحقول الإضافية وسجل النسخ تحفظ في `extra` الموجود؛ لا جدول أو migration أو تعديل RLS.

إلغاء الحجز له هوية طبيعية واحدة دون C/B/S ودون معرف قراءة المصدر أو شهره أو تصنيفه؛ نقل التصنيف لا يخلق إلغاءً ثانيًا. الحوادث المالية تحتاج معرف الحدث، وتطابق الوقائع مع معرفات مختلفة يوقف الإضافة للمراجعة. لكل حفظ بصمتا الطلب والحالة، ومفتاح طلب ثابت، ونسخة متوقعة. يعاد فحص العضوية والمصدر والربط والأقفال داخل المعاملة عند كل محاولة. التصحيح يحتفظ بـ`original` ونسخ before/after، ولا حذف أو استبدال صامت. تغيير شهر واقعة قائمة يحتاج معالجة مستقلة.

الأقفـال: فترة مقفلة، تسوية معتمدة/مرحلة، مسير معتمد/مدفوع، واقعة مستهلكة/مدفوعة، أو اعتراض مقبول تمنع الحفظ. لا تُفك حماية ولا يُعدل مسير قديم. الربط يجب أن يكون وحيدًا برقم سويتر وتاريخ العمل، ولا إنشاء عامل أو ربط بالاسم تلقائيًا.

**التسجيل هنا لا يخصم راتبًا ولا عمولة، ولا يضيف تعديل تسوية الشركة أو قيدًا أو سدادًا.** الواقعة مسندة للعامل للمراجعة والتتبع، وتظل `payrollApplied: false` و`ledgerPosted: false`. تنفيذ أي تحصيل أو خصم راتب لاحق يحتاج مساره وتفويضه، مع استهلاك هوية الواقعة مرة واحدة.

```json
  "periodKey": "2026-10",
  "metricKey": "cancelledByBiker",
  "sourceId": "C-5573245",
  "snapshotId": "ops-retro-cancellation-facts-20261028-v1",
  "bikerId": "<existing verified worker id>",
  "expectedRevision": 0,
  "reason": "إسناد إلغاء بسبب البايكر بتوجيه هادي؛ بانتظار تفاصيل سويتر",
  "decisionReference": "01a18461-252a-7032-b787-34a1206a9171"

```

المثال ليس أمر حفظ. مدير العمليات يطابق هوية العامل والمصدر ويعاين ثم يحفظ الجزء المثبت فقط، ويتحقق بالقراءة. 1983 غير مربوط؛ لا يُخمّن عامل بدلًا عنه. مهندس النظام يختبر الحفظ في البيئة المعزولة فقط، والإنتاج قراءة ومعاينة.

## مبلغ فعلي من فاتورة الحجز

إذا قرأ مدير العمليات خصمًا فعليًا في Invoice للحجز، يضيف الدليل التالي إلى `notes` في **قراءة خام جديدة عبر operationsv2 القائم**، مع إبقاء السبب الأصلي والأصل التاريخي. لا حقول مصدر جديدة ولا تعديل مرسل أو بصمات. حفظ الملاحظة لا ينشئ خصم العامل تلقائيًا.

السطر يبدأ `SSP_INVOICE_DEDUCTION_V1=` ثم JSON واحد بهذه المفاتيح فقط:
`bookingId, driverExternalId, serviceDate, cancellationReason, sourceReadAt, sourceUrl, currency, optimalAmountSAR, deductionLabel, signedDeductionSAR, netAmountSAR, observedText`.

المبالغ من النص الفعلي، و`currency` = `SAR`. `deductionLabel` يطابق `Booking Cancelled (Reason N)` كما ظهر. `signedDeductionSAR` سالب، و`observedText` النص الآمن الفعلي لقسم Invoice شامل `Optimal Amount` و`Deductions` واسم الخصم و`Net Amount` والمبالغ. الوقت ISO من قراءة المصدر، لا وقت الحفظ، ولا بيانات عميل شخصية.

الخادم يرفض دليلًا ناقصًا أو مكررًا أو مخالفًا لهوية الحجز/العامل/التاريخ/الرابط، أو معادلة الإجماليات، أو مبالغ النص. المعادلة بالهللات: Optimal + signed deduction = Net. يأخذ القيمة المطلقة **لبند الخصم** فقط؛ لا يأخذ صافي الفاتورة. مثال الفرق الحسابي فقط: 20 − 129.95 = −109.95، فالخصم 129.95 لا 109.95. العدد يبقى 1، ومطابقة Compensations تبقى false حتى وصول جدولها. لا يُرسل هذا المثال كأنه دليل مصدر حقيقي.

## حجز قديم أُكمل بقرار المالك

قد يحفظ استيراد العمليات فاتورة جديدة في الخام ويترك حجزًا قديمًا وغسلته محميين. لا يُستبدل الحجز لمطابقة بصمة ملاحظات القراءة الحديثة. يبقى كل أصل ووقته ومنطق إكماله وسعره وعمولته كما حُفظ.

الربط البديل قرائي فقط، ويحتاج نتيجة الدفعة `protected_existing_record` و`bookingMustMatch:false`، مع صحة بصمة الحجز القديم داخليًا، وتطابق رقم الحجز وتاريخ الخدمة ورقم البايكر وحالة المصدر. يُعاد فحص العامل الداخلي، ومطالبة الهوية الطبيعية، والغسلة ورابطَيها الثلاثة ببصمات الاستيراد. يجب أن تكون الغسلة مكتملة بقرار المالك، وعمولتها غير مدفوعة، وألا توجد علامة ترحيل أو حماية مالية. أي تعارض حقيقي أو رابط متغير أو عمولة مدفوعة يوقف الإسناد. تحفظ بصمتا الخام والحجز القديم ودليل الروابط في واقعة المتابعة الجديدة؛ لا تكتب هذه المعالجة أي حجز أو غسلة أو مطالبة أو رابط.
