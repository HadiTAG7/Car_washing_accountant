# مراجعة تكتات التعويض والاعتراضات

الموقع: https://app.hadialghanim.com/?page=compensation_review
القسم: العمليات ← المتابعة اليومية ← مراجعة التعويضات والاعتراضات.

## الحفظ المدعوم للوكيل 8

لا أداة MCP لهذا السجل في الإصدار الحالي. الواجهة هي المسار المدعوم؛ لا يُستعمل SQL لحفظ حالة حقيقية.
افتح «للوكيل: تحديث حقائق المصدر والمسودة المقترحة»، ثم اختر ملف JSON الخاص أو الصق الحزمة.
اضغط «معاينة دون حفظ»، راجع التكت والتغطية، ثم «حفظ حقائق المصدر ثم التحقق بالقراءة».
تقرأ الواجهة السجل بعد الحفظ وتقارن النسخة وبصمة المصدر وحالة طلب الرفع.
عند انقطاع/غموض النتيجة توقف الكتابة، ثم أعد قراءة السجل قبل أي إعادة. لا مفتاح جديد لتجاوز نتيجة مجهولة.

عقد الحزمة الوحيد: `src/lib/compensationReview.js:sourceSchema`.
مثال وهمي كامل قابل للتشغيل: `functions/test/compensationReviewFixture.js:reviewSource`.
لا ترفع حزم SSP الحقيقية إلى Git أو fixtures أو وجهة عامة.

الحقول العليا: schemaVersion، ticketId، source، facts، amounts، attachments، timeline، analysis، objections، queueDisposition، historicalReference.
ticketId ثابت عبر الأشهر، بحروف كبيرة/أرقام/شرطة. تغيير شهر الخدمة لا ينشئ هوية جديدة.
source يحفظ URL وreadAt والتغطية والمرشحات والصفحات وحدود القراءة وآخر نطاق مكتمل.
facts تحوي الشكوى ورد الدعم والتعليقات والحجوزات وهوية البايكر ودليل ربطه والتواريخ الأصلية.
ticketDate اختياري لتاريخ التكت الموثق بالصيغة YYYY-MM-DD، مستقل عن تاريخ الخدمة.
استثناء أكتوبر يتبع تاريخ التكت ومرجع القرار، وليس تاريخ الخدمة.

amounts: customer_code، compensation، invoice_deduction، settlement، late.
القيمة المفقودة null؛ تبقى إشارة SAR الأصلية، والعدد والدقائق غير سالبين.
دقائق Late مستقلة ولا تتحول إلى ريال. لا جمع مالي أو استرداد أو تعديل تسوية في هذا المسار.

attachments تحفظ فهرسًا وروابط أصلية خاصة وحالة المشاهدة actual viewed/unavailable/missing/duplicate.
الموقع لا يحمل صور العملاء أو المقاطع ولا ينقلها إلى bucket عام.
روابط HTTPS فقط، بلا كلمة مرور أو token/signature/credential أو رابط MCP أو جلسة.
إذا لم يتوفر رابط آمن، احفظ url=null وحدد التعذر ورابط صفحة المصدر الخاصة؛ الرابط وحده ليس مشاهدة.

queueDisposition:
- eligible: مرشح للمراجعة إن لم يظهر أي OBJ سابق.
- historical_excluded: قرار ترك أكتوبر موثق؛ historicalReference وتاريخ التكت إلزاميان.
- historical_deferred: «التالي» تاريخيًا دون قرار ترك؛ مرجعه إلزامي، وليس قرار مالك جديدًا.
- prior_decision_unverified: قرار سابق لم تُحسم مراجعته، ويظل معزولًا.

الأرشيف والمؤجل التاريخي والاعتراضات السابقة تحفظ دون إجبار وجود حالة نشطة.
تحديث المصدر لا يعيد الاستثناء أو المؤجل التاريخي. يمكن حسم غير المتحقق إلى eligible إذا ثبت المرجع، مع حفظ الأصل.
إذا خرجت الحالة النشطة إلى الأرشيف لا تختار الجدولة التالية تلقائيًا.
المراجعة التفاعلية لها مؤشر حالة نشطة واحد، و«التالي» لا يصنع قرار ترك.

## قرارات هادي

المسار مستقل عن حزمة المصدر، مقصور على UID/email حساب هادي القائم مع تحقق الجلسة الحية والدور الحالي على الخادم.
المعرفان هنا لتقييد الميزة لا لإنشاء حساب أو تغيير أي دور/claims. لا يكفي علم admin داخل الحزمة.
لا أداة MCP لإنشاء قرار أو طلب رفع، ولا يمكن لحزمة المصدر حقن decision/submission/recordType.
الحسابات التي تشارك نفس هوية الدخول لا يمكن تمييز شخصها من JWT وحده؛ يفصل العقد والمسار مصدر الوكيل عن أفعال المالك، ولا يحق للوكيل ضغط أزرار هادي.

كل فعل يحفظ الفاعل والوقت والتكت ونسخة السجل والمسودة والنص.
«ترك»، «معلومات»، «مسودة»، «طلب رفع بالنص»، «التالي» أفعال منفصلة.
عرض تفاصيل الأرشيف لا يغير الطابور. إعادة مراجعته تحتاج فعل مالك مستقلًا «إعادة مراجعة بقرار هادي» وسببًا وتأكيدًا.
إعادة المراجعة تحفظ القرار القديم ولا تنشئ طلب إرسال.
طلب الرفع مربوط بالنص الحالي ونسخته؛ تغيير المسودة يبطل الطلب القديم.
وجود OBJ سابق يمنع طلبًا جديدًا مكررًا. Accepted من SSP ليس استردادًا أو عكس خصم.

## متابعة طلب الموقع

لا إرسال SSP في الموقع، ولا webhook أو مؤقت أو مراقب جديد.
queued يعني طلب هادي محفوظًا ينتظر قراءة الوكيل المحلي.
يسجل الوكيل قراءته في الواجهة؛ الحالة تصبح «الإرسال غير محسوم».
بعد تنفيذ مأذون في SSP والتحقق من OBJ، يحدث المصدر بما شاهده ثم يسجل إيصال OBJ المطابق للطلب.
الحالة sent لا تأتي من حزمة المصدر ولا من مجرد حفظ مسودة.
النتيجة غير المحسومة توقف تغيير المسودة أو إلغاء الطلب حتى فحص OBJ.
آخر قراءة SSP وآخر تحديث الموقع وآخر قراءة الوكيل أوقات منفصلة.

## التخزين والعزل

إعادة استخدام quality_objections: نوع ssp_ticket_review_v1 ونوع ssp_ticket_queue_v1، والحقول الجديدة في extra.
لا migration أو RLS أو مفاتيح أو مرسل عمليات أو جداول مالية.
status الجذري ticket_review، لا accepted الداخلية. قراء الاعتراضات الداخلية يستبعدون هذا النوع صراحة.
كل حفظ متفائل بنسخة متوقعة ومعرف إعادة، وفي معاملة واحدة مع الطابور والتدقيق؛ لا تحديث مصدر يمحو قرار المالك.
بصمة التغير الموضوعي منفصلة عن sourceHash الكامل؛ تحديث أوقات الفحص وحده لا ينسخ المحتوى أو OBJ كاملًا.
حد الحفظ يوقف التحديث برسالة واضحة بدل إسقاط التاريخ.

HTTP الداخلي للواجهة: POST /api/compensation-review مع Bearer من الجلسة الحالية.
عمليات read/source/owner/execution منفصلة ومحققة. تفاصيل الحمولات في functions/src/compensationReview.js.
لا استخدام يدوي لتوكنات أو SQL أو بدائل رفض أداة.

الاختبارات: وحدات وحفظ وهمي، ثم PostgreSQL جديد على loopback بصلاحية ledger_server وRLS الفعليين، وواجهة fixture منفصلة.
لا حالات حقيقية في بيئة الاختبار. التحقق الحي قراءة فقط؛ حفظ الحالات الفعلية عند الوكيل 8 المخول وحده.
