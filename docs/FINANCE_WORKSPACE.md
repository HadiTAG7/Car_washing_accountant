# مركز المالية

## حدود الإصدار

يجمع التنقل تحت «المالية» مع الاحتفاظ بمعرفات جميع الصفحات القديمة. الصفحات الجديدة `finance` و`finance_reports` و`finance_workbench` و`finance_payroll` للإدارة فقط، ولا تظهر في محاكاة الشريك. رابط الرواتب يعرض المسير الحالي في نفس مكون البايكر، ولا ينقل إدارة الموظفين أو ينفذ رواتب.

التقرير الإداري لا يستدعي أي عملية مالية. لا دفع أو إصدار فاتورة أو تقديم ضريبة أو تغيير فترات أو صلاحيات أو حذف أو تعديل قيد في هذا الإصدار. تقارير CEO ومجموعتها وخدمتها منفصلة.

## التقارير

`POST /api/finance-reports` يحتاج Firebase ID token ساريًا غير ملغى وعضوية إدارة حالية من الخادم، دون اعتماد على ادعاء دور في الطلب. `list` يعرض30 رأس تقرير مع مؤشر صفحة؛ `read` يعرض أحدث نسخة أو `revision` محددة، وتاريخ آخر30 نسخة؛ `save` يحفظ تقريرًا مراجعًا مع `expectedRevision`.

العقد في `src/lib/financeReportContract.js`: الفترة، وقت القطع بالرياض، الدور1/2/3، المراجع ووقت المراجعة، مؤشرات بأساسها وتغطيتها وحداثتها، تحذيرات ظاهرة، مصادر، حالات بمعرف ومسؤول وخطوة تالية، وتفاصيل جداول. `null` لا يُحول إلى صفر، ولا يجمع التشغيلي والمرحّل والتحصيل. إغلاق الحالة يحتاج دليل تحقق، والتحقق الذاتي لا يسمى مستقلًا.

هوية التقرير حتمية: `finance-YYYY-MM-DD-role-kind-from-to`. تحفظ المجموعة `finance_reports` الرأس، وتحفظ `revisions/000001` إلخ محتوى `reportJson` غير قابل للاستبدال وبصمته وهوية الناشر الفعلية. JSON يتجنب عدم دعم Firestore لصفوف الجدول كقوائم متداخلة. إعادة نفس المحتوى ترجع `duplicate`؛ اختلاف نفس النسخة يرفض، والتصحيح نسخة جديدة بسبب واضح. التقرير محدود96KB ولا يقبل أسرارًا أو روابط MCP السرية أو مراجع أقراص محلية.

لا تُمنح صلاحية قراءة/كتابة SDK مباشرة للمجموعة الجديدة، حتى للإدارة؛ الوصول المصرح عبر الخدمة وحدها. قواعد الحجب الافتراضية الحالية تكفي، دون تعديل RBAC.

أدوات MCP: `sweater_finance_reports` و`sweater_publish_finance_report`. الناشر يتحقق بقراءة النسخة نفسها بعد الحفظ، ويستخدم رمز الحساب الحالي والخدمة نفسها، وليس Admin SDK أو وجهة قابلة للاختيار.

«إضافة تقرير مراجع» في الموقع يقرأ ملف التقرير المتحقق، يعرض معاينته وتحذيراته ثم يحفظه عبر الخدمة ذاتها ويعيد قراءة النسخة. هذا بديل مدعوم عند تأخر تحديث قائمة أدوات الاتصال، لا حفظ مباشر في قاعدة البيانات. الخطأ أو غموض النتيجة لا يعرض نجاحًا ولا يعيد الحفظ تلقائيًا.

## صندوق العمل

`POST /api/finance-workbench` بنفس تحقق الهوية والإدارة. الأنواع المؤهلة: `variable/monthly/annual/startup`؛ لا القوالب المتكررة أو الرواتب أو السلف. العمليات منفصلة: `list/options/read/previewCapture/capture/preview/save/approve/post`.

- التسجيل مفتاح طلب ثابت ومعاينة قبل الحفظ؛ السجل يبقى غير مرحّل، ويمكن أن تبقى حقوله غير المحسومة ناقصة بدل اختلاق سداد أو ضريبة أو تمويل.
- التصحيح في المصدر نفسه فقط. لا نقل بين الأنواع/الآباء ولا حذف. المبلغ بالهللة والكمية مثبتة وتكلفة الوحدة مشتقة بدقة8 منازل دون تغيير الإجمالي. يحتفظ المورد والفاتورة والرابط وتاريخها والضريبة والتمويل والغرض والأدلة.
- المصروف له بصمة نسخة تشمل حقوله المؤثرة، وموافقة في `finance_reviews` مرتبطة بالبصمة وبمعاينة القيد. أي تعديل مؤثر أو تغيير المعالجة/الحسابات يبطل الموافقة؛ العلم القديم `approved` وحده لا يكفي.
- تزيد `finance_revision` مع الحفظ حتى عند إعادة نفس القيم، فلا يعود اعتماد قديم عند التراجع عن تعديل. `approve` يحتاج `sourceHash` و`postingHash` من القراءة الحالية؛ تغير السياسة بين القراءة والاعتماد أو إعادة طلب اعتماد قديم بعد تغير المعاينة يرفض. كشف التكرار يعاد داخل معاملة الترحيل أيضًا، لا عند التسجيل فقط.
- المدخلات الضريبية تحتاج مرجع مراجعة أهلية؛ المبلغ/النسبة من المستند، أو سياسة تاريخية تحقق منها المراجع بمرجع صريح، ولا تُفترض نسبة اليوم. لا يغير هذا أي إعداد ضريبي.
- تأكيد وسبب وبصمة معاينة لازمة للحفظ؛ المعاملة تعيد فحص الدور والمصدر والآباء والإجماليات والفترات والأقفال والقيود والمستند المكرر، ثم تسجل القيم السابقة/اللاحقة والفاعل في سجل التدقيق.
- نفس رابط المستند أو المورد/رقم الفاتورة على مصدر آخر يوقف المسار لحسم احتمال التكرار أو التجزئة الموثقة. لا تُحذف أو تكرر فاتورة لتجاوز الوقف. دعم اعتماد تجزئة المستند تلقائيًا ليس في هذا الإصدار؛ الحالات المركبة تبقى متابعة موثقة بدل دمجها افتراضيًا.
- الترحيل يعيد التحقق داخل معاملة `postSource` القائمة، بما في ذلك الباب القديم MCP/callable؛ يتحقق من التصنيف وبصمة المصدر والاعتماد ومعاينة القيد والفترات والدليل والحسابات. أي قيد سابق حتى المعكوس يمنع إعادة ترحيل المصروف هنا.
- يقرأ الترحيل القيد/القيدين المحفوظين وأسطرهما من `journal_entries.lines`، ويطابق التاريخ والحسابات والمدين/الدائن مع المعاينة. المجهول لا يعاد عميانيًا. لم يتغير مكان تخزين أسطر الدفاتر.
- اعتماد المصروف اليدوي لم يعد انتقالًا يطلق `autoPostOnApproval`؛ الترحيل خطوة صريحة مستقلة. بقية المسارات كالغسلات والسندات القائمة لم توسع صلاحياتها.

أدوات MCP: `sweater_finance_workbench` للقراءة والمعاينة، و`sweater_finance_workbench_save` لخطوة واحدة مؤكدة ثم إعادة القراءة والتحقق. أدوات التشغيل القديمة لا تمنح موافقة مالية أو تتجاوز شروط الترحيل الجديدة.

تسجيل المصروف القديم `sweater_record_expense` صار واجهة توافق للخدمة ذاتها؛ التسجيل الفعلي يحتاج كمية ورابط مستند وrequestId وبصمة معاينة وسببًا، ولا توجد كتابة SDK مباشرة أو افتراض نقد/سداد. الوسائط القديمة الناقصة تعطي معاينة إرشادية فقط، ولا يسمحconfirm وحده بحفظها. ترحيل الأنواع المالية اليدوية في `sweater_post_source` يتجه إلى `api/ledger` الذي يفرض اعتماد النسخة، وليس callable قديمًا. لا تتغير أذونات مستخدمي الشاشات الأصلية.

## الاختبار والتفعيل

اختبارات الوحدة: `npm test`، والواجهة: `src/components/__tests__/FinanceWorkspace.test.jsx`، وMCP: `mcp/test/financeTools.test.js`. الاختبار الحقيقي `server/__tests__/financeWorkflow.emulator.test.js` يتطلب محاكي demo على19080 وفق `firebase.finance-test.json`، ولا يعمل على مشروع الإنتاج. يستخدم قواعد الإنتاج لاختبار رفض الشريك والمشرف والمحاسب والمشغل للقراءة المباشرة ورفض تزوير الاعتماد.

على Windows يحتاج المحاكي Java21 ومسار إعداد/rules لا يحتوي حروفًا عربية بسبب عيب مسار Java؛ انسخ إعداد الاختبار وقواعد الاختبار إلى مجلد مؤقت ASCII ثم مرر `--config` لذلك الملف. لا توقف محاكيات فريق آخر. لا تنشر `firestore.test.rules` أو ملف إعداد الاختبار.

`node scripts/finance-preview.mjs` يعرض `/scripts/finance-preview/index.html` علىlocalhost5199 ببدائل صريحة لكل حدود البيانات والهوية، دون تحميل Firebase أو API حي. هذا فحص عرض ببيانات اصطناعية، وليس إثباتًا لاختبار خادمي/حفظ إنتاجي. ليس مدخلًا لبناء الإنتاج.

قبل التفعيل: أحدث مصدر إنتاج، اختبارات متأثرة ناجحة، فحص الجوال والكمبيوتر، توافق تطوير CEO، ثم Ready يطابق commit الرسمي وفحص حي قراءة فقط. نشر Vercel لا يثبت نشر Cloud Functions؛ أي callable إنتاجي مستخدم يجب أن يطابق حارس الاعتماد الحالي قبل إعلان اكتمال المسار. لا تعدل فاتورة أو ترحل مصروفًا تجريبيًا للتحقق.

التفعيل يبدأ الأرشيف ولا يستورد الأرصدة التاريخية على أنها حالية. تُنقل الحالات المفتوحة بمعرفاتها ووقت آخر تحقق الحقيقي؛ تبقى Drive والأدلة المحلية ومحاضر التدقيق محفوظة. التعليمات التشغيلية في `docs/finance-agent-workflow.md` ولا تغير الجداول أو الإخطارات أو النماذج.
