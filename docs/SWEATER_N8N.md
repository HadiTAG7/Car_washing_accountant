# n8n Cloud wash import

This is a dedicated incoming integration for the accounting platform. It
does not log in to SSP, transfer a ChatGPT session, or replace source extraction.
The existing ChatGPT/HMAC integration remains unchanged.

## Provisioning

An administrator opens **تكامل سويتر → إنشاء اتصال n8n**. Creating a key is an
explicit action, never a page-load effect. The secret is displayed once. The
database stores a SHA-256 hash, never a recoverable secret. Keys expire after
90 days and can be revoked using the existing integration key controls.
Creation uses the admin-guarded `sweaterCreateN8nKey` server action.

The key has only scope `n8n_wash_ingest` and principal `n8n-wash-sync`.
It cannot authenticate on the HMAC endpoint, ledger API or account management.
No new table, database grant, environment secret or migration is required.

## n8n credential

Download the workflow from the same platform page, or import
`public/integrations/sweater-n8n.json`. It is generated by
`node scripts/generate-n8n-workflow.mjs` and contains no credentials or live data.

Create a **Header Auth** credential:

| Field | Value |
| --- | --- |
| Name | `Authorization` |
| Value | `Bearer <the one-time key>` |
| Allowed HTTP request domains (when available) | `app.hadialghanim.com` |

Select that same credential in **all four HTTP nodes**. Keep keys in n8n's
credential manager, never workflow code, node headers, URLs, input or logs.
Each node pins the endpoint and disables redirects and automatic retries.

## API

`POST https://app.hadialghanim.com/api/integrations/sweater/n8n`

Only `preview`, `save` and `status` are accepted, with the same exact bodies,
contract v2 payload, limits, preview hashes and response shapes documented in
[SWEATER_OPERATIONS_SYNC.md](SWEATER_OPERATIONS_SYNC.md). The route calls the
same validation, atomic writer and readback functions; there is no second
wash-writing implementation. Metrics and administrative completion are not
available here. Authentication is HTTPS Bearer, distinct from the existing
HMAC protocol; do not change old credentials or send HMAC keys here.

The endpoint enforces active status, credential family, scope, principal,
expiry, constant-time full-token hash comparison and 30 requests/minute/key.
Only the Authorization header is accepted. Responses are `no-store`; errors
never echo the token. Preview/status update key usage and rate metadata but
do not write business records. List operations return only public metadata.

## Workflow and recovery

The template is a sub-workflow with one input item `{payload: <v2 batch>}`.
Source extraction must supply real IDs, statuses, service dates, worker links,
source timestamps and honest individual/B2B page coverage. At most 100 records
per batch. Never fabricate times, infer service types from prefixes, or include
customer PII or login data. Incomplete execution stays review-only under the
existing contract; this integration does not add an owner-completion shortcut.

1. Read `status` for the exact complete payload/run ID.
2. If already found, require `verified:true` and finish without another save.
3. Otherwise preview. Any rejected rows stop the workflow for review.
4. Save the unchanged payload with both returned hashes.
5. Read status again and require full verification before reporting success.

A save timeout or lost response stops this execution. Restart with the same
immutable payload/run ID so the first status check resolves it; never create
a fresh ID to work around uncertainty. Changed payloads return 409, stale
previews 412, invalid/expired/revoked credentials 401, rate excess 429. No
automatic logical/auth retry. Preserve the input outside transient execution
state until the run is verified. Serialize source runs that overlap records.
Do not add a schedule until source access and credential selection are ready.

Testing uses synthetic isolated data. Do not save a real SSP booking as a
software test. Production readiness requires a real authorized source run
and verified readback; a successful deploy alone does not establish that.
