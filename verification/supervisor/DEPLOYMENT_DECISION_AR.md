# قرار النشر

لا نشر أو تفعيل الآن. الفرق الحالي لا يحتوي feature flag افتراضيًا مغلقًا. عدم إنشاء حساب ليس تعطيلًا تقنيًا، ولم نفحص وجود عضويات supervisor حالية في الإنتاج.

Firestore وStorage متاحان للعميل مباشرة؛ رفض API أو واجهة قراءة فقط لا يستبدلان قواعد الوصول. القواعد الأساسية تمنح العضويات المسجلة قراءة خامًا، وعلامة مدير قديمة قد توسع الإذن. API الجديد يستخدم dispatch المعدل، لكن Functions المنشورة تظل نسختها القديمة حتى نشر مأذون منفصل.

callLedger يختار HTTP عند ضبط VITE_LEDGER_API_URL، وإلا Functions؛ لا نفترض قيمة البيئة الحالية أو توقف الباب الآخر. لذلك لا نعتمد نشر الفرق الحالي في الإنتاج كميزة «معطلة» دون تحقق القواعد وكل باب خادمي قابل للوصول.

يمكن إجراء معاينة معزولة لا ترتبط بقاعدة إنتاج. إصدار إنتاج مطفأ يتطلب عملًا منفصلًا مراجعًا: بوابة خادمية مغلقة افتراضيًا للعمليات الجديدة ومسار عضوية/واجهة مغلق، وفحص عضويات supervisor ومسارات Functions/Firestore/Storage القائمة. لا يدعي flag خادمي حجب الوصول المباشر بالقواعد القديمة. لم يُنفذ ذلك هنا.

بعد نجاح التحقق والتفويض الصريح:

1. راجع بالقراءة أثر رفض الأدوار الناقصة؛ لا تصحيح أو ترحيل عضويات تلقائي.
2. نسق القواعد وHTTP وFunctions وStorage حيث يستخدم. ليست هناك عملية ذرية واحدة بين Vercel وFirebase؛ يمكن النشر على مراحل مع بقاء العضوية غير مفعلة حتى اكتمال جميع الحماية والتحقق من النسخ.
3. فعّل الحساب المحدد بتفويض عضوية صريح بعد اكتمال الحماية. نشر الواجهة وحده غير كافٍ.

npm run deploy القديم مسار Firebase وليس نشر واجهة. بوابة prebuild تبقى كما هي، وترفض الفرع/SHA الخطأ أو تعذر التحقق. أساس حزمة الاختبار لا يضمن رأسًا رسميًا مستقبليًا.
